# DEF CON 34 Badge — Firmware Verification

Your badge runs a Baochip-1x SoC. This guide walks you through checking that the
bootloader firmware on it corresponds to the published source code.

There are two levels, and you can stop after the first:

1. **Read your badge's state** — five minutes, needs only a serial terminal.
   Tells you whether the badge is in a healthy, expected configuration and lets
   you compare its firmware hashes against published values.
2. **Rebuild the firmware yourself** — needs [GNU Guix](https://guix.gnu.org/)
   and a few hours the first time. This is the actual reproducibility check.

For the full trust model — what any of this proves, and what it assumes — see
[VERIFY.md](VERIFY.md). The short version is at the end of this file.

---

## Step 1: Read your badge

Connect over USB serial. On Linux the badge shows up as `/dev/ttyACM0`:

```bash
tio /dev/ttyACM0
```

Press Enter, then type `audit`. Do this yourself, and read the output from the
top — a transcript someone hands you establishes nothing.

### 1a: Health checklist

Your badge is **pre-production silicon running beta-signed firmware**, and its
audit output reflects that. Both are expected. Here is how to read every line
that matters:

| Line | Expected on a DC34 badge | What it means |
|------|--------------------------|---------------|
| `Board type reads as:` | `Oem` | Determines which package you rebuild in Step 3. |
| `Boot partition is:` | `Ok(PrimaryPartition)` | **Important.** If this says `AlternatePartition`, the running boot1 is the image at `0x6006_0000`, but `audit` always hashes the partition at `0x6002_0000` — so the `boot1 code only` value would be for code that is *not running*. |
| `Stepping is:` | `A0` | Pre-production silicon (expected for a badge). On production A1 silicon the boot0 write protection is hard-wired on; on A0 its runtime control can be cleared. Whether that fully unlocks boot0 is not something we can state from public documentation. Either way, a badge is a weaker platform than shipping Baochip hardware — treat it as such, and don't rely on it as a production security device. |
| `Revocations:` | all `enabled` | Key revocations are permanent and one-way. If the Baochip keys were revoked, the badge would accept firmware signed by the public developer key. |
| `Boot0: key n/n (tag)` | `0/0 (bao1)` | boot0 is signed with a Baochip **production** key. |
| `Boot1: key n/n (tag)` | `2/2 (beta)` | boot1 is signed with the **beta** key, which lives in a secured token but is also present in a development environment. Weaker than production, and expected for a badge. **`dev` here would be a red flag** — that key's private half is public, so anyone could sign firmware your badge would boot. |
| `Erase proof:` | `uninit or access denied` | Informational. |
| `Collateral erased` | present | Normal for Baochip-signed firmware. |
| `In-system keys have been generated` | present | Provisioning completed. |
| `CM7 & debug confirmed fused off` | present | Hardware debug and the secondary core are fused off. If you instead see `Factory configuration error`, the badge can be driven externally. |
| `Boot1 receipts OK` | present | The boot1 signing keys have not changed since last boot. |
| `Boot1 anti-rollback OK` | present | Rollback counter agrees with the image. |
| `== IN DEVELOPER MODE ==` | **absent** | If present, the badge has booted developer-signed firmware, its secrets are erased, and nothing it reports is trustworthy. |
| `== BOOT0/BOOT1 ... PUBKEY CHECK FAILURE ==` | **absent** | Keys in the boot images do not match the indelible reference copies. |
| `== CP SETUP FAILED ==` | **absent** | Factory provisioning did not finish. |
| `** System did not meet minimum requirements for security **` | **absent** | Printed if *any* of the above failed. Treat it as a hard stop. |

### 1b: Record these values

```
boot0 code only:        <128 hex chars>
boot0 baobit toolchain: <40 hex chars>
boot1 code only:        <128 hex chars>
boot1 baobit toolchain: <40 hex chars>
```

**The two toolchain commits are usually different.** boot0 and boot1 are built
and released independently, and each image records the baobit commit that built
it. Use the **full 40 characters** of each — not a truncation.

## Step 3: Rebuild from source

### Which packages to build

boot0 is common to all boards, so it is always `bao1x-boot0`. boot1 has
board-specific variants:

| `Board type reads as:` | boot1 package | make target |
|---|---|---|
| `Oem` (DC34 badge) | `bao1x-boot1-lite` | `boot1-lite` |
| `Dabao` / `Baosec` | `bao1x-boot1` | `boot1` |

To confirm, look at the header comment of
`channels/baobit.<first-8-of-boot1-commit>.scm` in the repo — it names the
package that commit is meant to build.

### Build

Each image is built at **its own** toolchain commit, so this is two checkouts.

```bash
git clone https://github.com/sbellem/baobit && cd baobit
```

**boot0**, at the `boot0 baobit toolchain` value from Step 1b:

```bash
git checkout 441559d7e1984623ec0a52f60f90240c740b6c41
make boot0 ROOT=boot0
sha512sum boot0/bao1x-boot0-presign.img
```

**boot1**, at the `boot1 baobit toolchain` value:

```bash
git checkout 4be6e2d6f6a694942ef6cc333ff2b91f73966644
make boot1-lite ROOT=boot1
ls boot1/
sha512sum boot1/*-presign.img
```

Substitute your own commits. Note that `bao1x-boot1-lite` does not exist at
every commit and the badge commits are not necessarily on `main` — the
`git checkout` step is required, not optional.

Everything else is pinned by the commit you checked out: the Guix revision comes
from `channels/guix.scm` in that tree, and the package definitions come from
`packages/` in that same tree. Nothing is fetched from a moving branch.

### Compare

The `sha512sum` of each presign image should equal the corresponding
`code only` value from Step 1b.

### Forcing a real rebuild

Guix may satisfy a build from a substitute server rather than compiling locally,
in which case you have confirmed that your build inputs match the server's — not
that you reproduced the output. To rebuild for real and error out if the result
differs:

```bash
make boot0 CHECK=1
make boot1-lite CHECK=1
```

This is much slower. The first build compiles the Rust toolchain from source.

## Step 4 (optional): Verify the official signed images

The signed release images carry Ed25519 signatures you can check independently:

```bash
guix shell nss-certs rust rust:cargo -- cargo build --release --manifest-path tools/Cargo.toml

VERSION=v0.10.1
RELEASES_URL="https://ci.betrusted.io/releases/${VERSION}/baochip/bootloader"
curl --proto '=https' --tlsv1.2 -sSfLO "${RELEASES_URL}/bao1x-boot0.img"

./tools/target/release/verify-binary bao1x-boot0.img
```

Two lines cross-check against your badge:

- `Presign SHA512` should equal `boot0 code only`
- `Padded SHA512` should equal `boot0 partition`

## What this proves — and what it doesn't

**If everything matches, you have shown:** the code region of your badge's
bootloaders is byte-identical to a build from the named baobit commits, and
those commits build reproducibly from published source.

**You have not shown that those bytes are what is executing.** The `audit`
command is a program running in boot1 that reads boot0 and boot1 out of memory
and prints hashes over an unauthenticated serial line. There is no signature, no
nonce, and no binding to your physical badge. A modified boot1 could print the
expected values. The measurement comes from inside the thing being measured.

**Nor have you verified the source itself.** Reproducibility proves the binary
came from a named source tree. It says nothing about whether that source is
benign — no step here reads the xous-core code.

**And the whole chain assumes the chip probe station burned what the release
pipeline produced.** boot0, boot1, the public keys, and the lock fuses are all
written at that one step, and every on-device check compares against a value
written there. That assumption is not checkable in software.

On A0 silicon, additionally, the runtime control for boot0's write protection
can be cleared. Whether that is enough to actually rewrite boot0 is not
something we can confirm from public documentation, but it means A0 gives a
weaker immutability guarantee than production A1 silicon.

None of this makes the exercise pointless — it detects tampering after
manufacturing, confirms the published firmware is reproducible, and tells you
your badge is in a known configuration. It is just worth knowing exactly which
claim you have established. [VERIFY.md](VERIFY.md) lays out the full assumption
set.

## Troubleshooting

**`guix build: error: bao1x-boot1-lite: unknown package`**
You did not check out the boot1 toolchain commit, or you checked out the wrong
one. That package does not exist at every commit.

**Hash mismatch on boot1**
Check `Board type reads as:` and confirm you built the right variant —
`bao1x-boot1-lite` for `Oem` badges, `bao1x-boot1` otherwise.

**Hash mismatch on either**
Confirm you used the full 40-character commit, and that you used *each image's
own* toolchain value rather than the same one for both.

**The build takes forever**
Expected on the first run — the Rust toolchain is compiled from source.
Subsequent builds reuse the store. Substitutes are enabled by default and help
considerably.

**`audit` prints fewer lines than shown here**
Older firmware prints less; `Stepping is:` in particular was added after the
v0.9 series. If a line in the checklist is missing, you cannot check that item
on your firmware revision.

**Something in the checklist failed**
File an issue at https://github.com/sbellem/baobit/issues with your `audit`
output. Redact `Device serializer`, `Public serial number`, and `UUID` if you
would rather not publish identifiers.
